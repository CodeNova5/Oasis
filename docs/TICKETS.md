# Ultimate NetGuard AIO: Product Tickets

This backlog implements [PRD.md](PRD.md). Tickets are ordered by dependency inside each phase. `P0` means required for the first release of this product direction; `P1` means important follow-up; `P2` means optional or later.

## Ticket conventions

- **Type:** feature, refactor, bug, test, documentation, or security.
- **Status:** `Done`, `Partial`, or `Not started`, summarized in [Current status](#current-status). A ticket with no status line is `Not started`.
- **Dependencies:** tickets that should land first.
- **Acceptance criteria:** observable completion conditions.

### NG-015 Migrate Data Saver classification to identity groups

- **Status:** Partial — `src/network/bandwidthguard.*` now classifies a process from evidence rather than only from its file name. `ClassificationEvidence` carries the PID, executable name and path, the NG-010 identity and display name, the NG-011 publisher and signer status, the NG-012 service flag, and the NG-014 group id and name, and a second `classifyProcess()` overload takes it. The twelve rules that shipped before NG-015 still run first and unchanged, so every category the product already assigned is the category it assigns now, and `pid 4` and services are still `Protected`. Only when a name has no rule does the publisher and product metadata decide: a signed "Google Chrome" is AskFirst and "Google Update", "Microsoft Edge Update", "Brave Update", and "Microsoft OneDrive" are AutoCandidate, with updater fragments ordered before the application they update because "Microsoft Edge Update" also contains "edge". ### NG-054 Add top-consumer dashboard

- **Type:** feature
- **Priority:** P0
- **Dependencies:** NG-040, NG-051, NG-052
- **Goal:** Show current top consumers, active controls, unresolved traffic, and recommended actions at a glance.
- **Acceptance criteria:** The top consumer can be inspected and controlled from the first dashboard view.

- **Status:** Done — `src/network/topconsumers.*` is a widget-free reading of one snapshot: it ranks consumers by current combined rate, then total bytes, then name (then pid), so a refresh does not make equal consumers jump rows. `isUnresolved` is the honest definition this build can support: no executable path to act on, or no activity classification to explain the traffic. `build()` returns display-ready rows plus totals, the top consumer's identity and headline, the policies that are in force right now (evaluated through NG-023, so an expired or disabled policy is not called a control), the NG-053 enforcement line for each, the unresolved count and bytes, and up to three NG-042 suggestions.

- `src/network/dashboardpanel.*` renders that summary above the process tree in the Network tab. It shows a bold headline (`chrome.exe is the top consumer at 1.2 Mbit/s`), a detail line with identity, usage, and control, a five-row table (consumer with identity, usage, activity, control), the controls in force with their effect, enforcement, and expiration countdown, the unresolved line, and the suggested actions with their reasons. Rows are click-through: clicking a row or **Details...** opens the NG-052 detail view for that consumer; **Suggested action...** opens the NG-042 recommendation for the selected row (or the top consumer when nothing is selected); **Policies...** opens the stored-policy list. The panel owns no manager and applies nothing, so it cannot become a second enforcement path.

- `NetworkWidget::refreshDashboard()` builds the consumers from the live `ProcessRowSnapshot` rows, resolves each image path once per `(pid, start time)` (cached, so a one-second refresh does not open a process handle per row), reads block/throttle state and the owning policy, computes suggestions only for the rows the panel shows, and pushes the result. It is driven by the existing once-a-second speed update plus capture start/stop, clear, policy edits, block/unblock, and throttle results, so there is no new timer or thread.

### NG-055 Add audit and attribution export

- **Type:** feature
- **Priority:** P1
- **Dependencies:** NG-050, NG-036
- **Goal:** Export filtered JSON/CSV evidence for support and personal analysis.
- **Acceptance criteria:** Export includes schema version and confidence; destination redaction is enabled by default.

- **Status:** Done — `src/network/evidenceexport.*` owns both formats and is pure: it takes the rows the view currently shows and returns the bytes to write, so the envelope, the CSV escaping, and the redaction rules are testable without a dialog or a file. `AuditEventStore::exportJson(events, redact)` and `exportCsv(events, redact)` delegate to it. JSON keeps the NG-050 envelope (`format`, schema 1, `exportedAt`, `redacted`, retention, count, events) and gains the redaction flag; CSV opens with `#`-prefixed metadata lines carrying the format, schema version, export time, and redaction state, then one documented header row and one row per event, quoting a field only when it contains a comma, a quote, a line break, or edge spaces. Nothing outside the contract is written, and no packet payload exists to write.
- The attribution export is new: `NetworkMonitor::attributionSummaries()` snapshots every live address from the NG-031/NG-032 correlator as one combined summary, and `EvidenceExport::attributionJson`/`attributionCsv` write `format` = `netguard.attribution`, schema 1, the redaction flag, a count, and per destination the address, resolved name, every observed name, the source (`DNS answer`, `TLS SNI`, or both), the NG-035 confidence, the expiry, and the evidence lines. The CSV carries the same fields with a `confidence` column. The Settings **Attribution privacy** group's **Export attribution data...** action chooses JSON or CSV in the save dialog and appends the matching suffix when the name has none.
- Redaction defaults to the NG-036 `redactDestinationsInExport` setting (on) for both exports and for diagnostics, so there is one switch rather than three: an IPv4 address keeps its first three octets, an IPv6 address loses its last group, a host name keeps its top-level label (`***.com`), a port survives, and process names, executable paths, and file names are left alone because the redactor only rewrites destinations. Each file records `redacted`/`# redacted` and each success message reports it, so a verbatim export is never accidental.
- **Known limits:** the attribution export only contains what the correlator still holds — an address that was never resolved has no row, and lowering the retention window shortens the file; audit events carry no confidence field, so confidence appears only where the contract has it (the attribution export).
- **Validation:** `qmake tests/netguard_tests.pro && mingw32-make -j4 && ./netguard_tests` adds 47 checks: CSV quoting for commas, quotes, line breaks, and edge spaces; the audit JSON envelope, injected export time, redaction flag, and retention; verbatim versus redacted event reasons, addresses, and ports; executable paths surviving redaction; the audit CSV's four metadata lines, header, row count, and quoted comma field; the attribution JSON envelope with format, schema version, count, confidence, source, and every observed name; per-address and per-name redaction including the evidence lines; the CSV `confidence` column and joined name list; and both empty-selection files. It runs within the 1144-check harness with 0 failures, the NG-050 checks still cover the unredacted envelope and contract-only key set, and the application builds with `MAKE_EXIT=0`. Remaining: no CSV import, redaction is whole-text rather than field-aware for free-text details, and neither export dialog has been visually reviewed.
